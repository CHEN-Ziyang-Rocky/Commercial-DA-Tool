# 真实数据版本：集团法人实体与资料复核工作台

## 1. 为什么做这一轮，而不是继续加功能数量

旧版已经能支撑初级技术面试：JWT 权限、SQL 聚合、分页、Redis 缓存、错误处理和真实数据库测试都形成了完整链路。但它的经营指标来自练习数据，用户也需要手工输入国家、城市和层级。用于银行 Technology / Operations / Business Analyst 或集团 IT / 数据岗位时，缺少可解释的真实来源和具体工作任务。

本轮选择一个可以落地的范围：**管理与运营人员在会前查询集团相关法人实体，检查母子关系的证据与资料维护情况，导出待复核清单。** 用户提供的岗位列表用于选择场景，不将其中薪资、项目名称和招聘状态视作已核实事实。

这不是完整的集团内部管理系统，不承诺满足所有面试；也不能证明本轮新增功能曾在 bilibili 实习期间上线。面试中应区分实习贡献、后续复盘与个人扩展。

## 2. 用户、任务、可验收结果

| 用户 | 实际问题 | 操作与结果 |
| --- | --- | --- |
| 集团运营/管理助理 | 我关注的集团涉及哪些法人、分布在哪些地区？ | 选择 Review portfolio；查看实体数量、法定地址地区分布；打开实体详情 |
| 数据运营 | 哪些 LEI 过期或关系记录需核实？ | 点击 Needs data review / Lapsed LEIs，查看具体原因并导出 |
| 客户资料维护人员 | 这家公司是否有名称变更？直接母公司是谁？ | 按 LEI、法律名称或其他名称检索；阅读来源关系状态和例外原因 |
| 会议准备人员 | 如何把本次筛选交给同事继续复核？ | 导出全部匹配记录；CSV 包含来源 URL、更新时间、快照时间和复核标记 |
| 技术人员 | 外部 API 失败时会不会破坏正在使用的数据？ | 采集成功后才发布快照；校验通过后在 MySQL 事务中整体替换；失败保留原库 |

当前仅提供“形成清单”，不假装已有审核指派、审批签字、监管报送或实际 KYC 决策流程。

## 3. 真实数据从哪里来

数据来自 GLEIF 官方 API，LEI 是法人实体标识符，用于区分名称相近的公司。公开数据依 [GLEIF 数据使用条款](https://www.gleif.org/en/meta/lei-data-terms-of-use) 以 CC0 提供。本项目独立开发，不代表 GLEIF 或样本企业认可。

固定的八个检索起点在 [seeds.json](../backend/registry-data/seeds.json)：HSBC、OCBC、China Everbright Bank、DBS、AIA、HKEX、Swire Pacific、CLP。标签及行业是我们组织演示场景的编辑分类，不是来源为每个下属实体提供的行业认定，也不等于法律上最终集团母公司。

采集范围：

1. 读取八个起点的官方 LEI 记录。
2. 取它们所有分页的直接下属实体，再展开一代。
3. 读取范围内实体的直接/最终母公司关系或报告例外。
4. 将缺失的直接/最终母公司实体补入作为上下文；不继续无限扩展这些上下文实体。
5. 保留所有来源状态；只有关系 ACTIVE 且关系登记 PUBLISHED 才进入当前关系链。

2026-10-21 的快照有 **221 个实体、38 个法定地址国家/地区、41 个法律辖区值**，其中 181 个 LEI 状态为 ISSUED，40 个为 LAPSED。数量随真实披露变化，代码没有设定“必须等于 221”的业务规则。限制 3,000 条是小型复核工作台的资源保护：超过时明确失败，不静默截断。

记录位于 gleif-snapshot.json，原始响应位于 gleif-source-responses.json。记录提供原始查询 URL、登记更新时间、下一续期时间、抓取时间及原始关系证据，快照含来源发布批次与内容摘要。

**为何不把 2,000 条数据随意改成 1,973 条？** 数字不整齐并不代表真实。真实应来自可复查的数据、明确选择规则，以及对缺失/过期的准确表达。

## 4. 最重要的业务口径

- GLEIF 的直接/最终母公司关系是**会计合并关系**，不是持股比例；分支机构也不能直接等同于子公司。[官方说明](https://www.gleif.org/en/lei-data/access-and-use-lei-data/level-2-data-who-owns-whom)
- 没查到子公司，只代表当前来源或采集范围没有符合条件的记录，不代表公司没有子公司。光大、中电样本就能帮助讨论这个限制。
- Reporting exception 是来源报告的一种情况，例如 NATURAL_PERSONS；不能一律当成数据错误，也不能一律显示“集团根公司”。
- Entity ACTIVE 与 LEI ISSUED/LAPSED 是不同状态；LEI LAPSED 不代表企业破产、失去银行牌照或信用恶化。
- 法定地址地区不等于所有营业地区，也不一定等于法律辖区。页面指标已分别命名。
- “Review portfolio”是所选起点及两代报告实体组成的复核范围，可能含待核实的历史关系；正式关系链只使用有效且发布的直接关系。
- 下属法人数量不能直接衡量集团规模、盈利或风险。没有可靠口径的营收、员工数、持股比例，不填随机值，也不把缺失当零。
- 旧版经营分析放在独立的 Demo 菜单，所有页面标明模拟/练习数据，不与真实实体按名称拼接。

## 5. 使用方法：先从一个完整任务学起

### 已有数据库升级

在 backend 目录，沿用你的本地 `.env`：

```bash
npm ci
npm run registry:init
npm run registry:import
npm run build
```

`registry:init` 只新增 registry_entities / registry_dataset 两张表，不修改公司、账号表。不要因为这次升级对已有库执行 db:init 或 schema:sync。

重新构建前端并重启应用后，登录首页就是 Entity review。仍使用已有账号权限；所有 registry API 需要登录。

### 从零安装

按 部署教程 初始化空库、账号、服务。空库初始化已包含新表，再运行 registry:import。快照随代码一起上传，不需要上线时实时访问 GLEIF。

### 演示一个具体任务

1. 以普通访客登录，首页查看整个样本概览。
2. Review portfolio 搜索 OCBC 并选择：看到 12 个范围内实体；此数值属于本次快照。
3. 再选择 Hong Kong 地区，解释多条件 AND、多个地区 OR。
4. 清除地区，打开母公司或子实体详情，阅读直接母公司与最终母公司的区别。
5. 点击关系来源，核对它的 ACTIVE / PUBLISHED 状态；不要只凭品牌名认定归属。
6. 回到首页点击 Lapsed LEIs，导出清单；解释复核动作是核实更新状态，不是判定信用风险。
7. 切换到 Demo analytics，演示旧版的 SQL/Redis 经营分析，并主动说明这套指标是模拟数据。

## 6. 采集、校验、导入和查询如何工作

### 数据更新

```bash
cd backend
npm run registry:fetch
npm run registry:import
```

fetch 是命令行工具，没有开放给普通访客的在线抓取入口。它只访问固定 GLEIF API 来源，最多三个并发请求，带超时、重试和分页；不需要 API 密钥。全量采集完成后写入临时文件并替换快照文件。正式更新前保留上一次快照和数据库备份，查看采集范围、数量与状态变化。

import 先检查 LEI 唯一性、字段、关系方向与类型、引用和有效关系环路，再在单个事务中替换 registry 数据。已有 company/users 数据不受影响。导入器对 dataset 行加锁，串行化并发导入；重复导入不会产生重复实体。原始关系例外与状态仍保留在 JSON 字段，不能为了画树而丢弃。

每次查询在 REPEATABLE READ 事务中读取元数据和实体，避免元数据与实体分属两个批次。当前范围很小，采用**有上限的快照内筛选与关系遍历**，没有谎称它是大规模 SQL 搜索引擎。若扩展到整个 LEI 索引，应改为分页 SQL、搜索索引、独立边表与增量导入，而不是取消 3,000 条保护。

该模块不复用模拟经营数据的缓存，以免混淆快照版本或陈旧关系；旧的 company 模块仍展示 Redis 缓存策略。外部 API 不参与用户页面请求，因此其暂时不可用不会中断已导入快照的查询。

### 新 API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /registry | 过滤、分页、统计、可选项与来源元数据 |
| GET | /registry/:lei | 证据、父级链、有效直接子实体与范围说明 |
| GET | /registry/export | 导出全部匹配结果，忽略分页，不绕过筛选 |
| GET | /company/options | 旧版经营数据的真实可选层级、地区、城市 |

查询参数：q、country（可重复）、group（起点 LEI）、status、quality、page、limit。名称检索包含来源提供的其他/历史名称；不保证能够识别未提供的品牌简称或中文译名。前端搜索防抖，切换筛选重置页码，旧请求会取消；CSV 转义引号与危险公式前缀。

## 7. 对不同岗位怎么讲

| 方向 | 更有说服力的重点 |
| --- | --- |
| 银行 Technology / 软件开发 | 身份权限、外部数据接入、事务导入、关系边界、接口测试、发布验证 |
| 数据分析 / Business Analyst | 用户故事、字段口径、缺失与零、来源追溯、筛选体验、可验收清单 |
| Operations / 客户资料维护 | 实体识别、登记状态复核、更新时间、异常处理、交接导出 |
| 大型集团 IT / 管培 | 跨地区实体可见性、母子关系、管理层会议准备、信息完整性 |
| 量化 / 投行前台 / 投资研究 | 此项目只能作为工程与数据处理经历，不能替代概率统计、金融建模、估值、市场理解或研究成果 |

不要对银行说“我已经做了生产级 KYC/反洗钱/授信系统”，也不要对管理层说这是完整股权图谱或合并报表。一个范围清楚、确实能运行的系统比过大的能力声明更经得起追问。

## 8. 面试准备的完成标准

你应能独立完成：从需求写一个验收条件；解释一个真实实体的证据；用自己的话区分三种状态；追踪一次前端到 MySQL 的请求；给筛选新增一项并测试；解释快照更新失败和导入失败分别会怎样；解释何时需要升级架构。

达到这些标准后就可以开始面试，不需要继续等待更多功能。项目不能保证所有岗位录用，但现在已经有业务场景、公开真实数据、交互、可追溯性、数据质量边界及工程验证可供讨论。
